# Historical image recovery — separate approval required

**Superseded destination:** the current recovery target is Hostinger `UPLOADS_DIR`, using the non-overwriting filesystem utility documented in [PUBLIC_UPLOADS_READINESS.md](PUBLIC_UPLOADS_READINESS.md). Do not execute the Cloudinary destination steps below; they describe the earlier proposal. The source-inventory and missing-original limitations still apply.

This procedure is prepared, not executed. New uploads going to Cloudinary does not recover historical missing files and does not change old `/uploads/...` or `/api/image/...` references automatically.

1. Create a read-only inventory of database image references using the production schema, restricted to public media fields: category/product/new arrival/promotion URLs, product listing URLs, vendor store logo/banner URLs, Want photo/photos and review imageUrl. Include existing public ProductImage binary rows as a distinct source, not as missing disk files. Do not export private customer information, payment proofs, support attachments, vendor identity or appeal files.
2. Inventory actual available originals from current/previous Hostinger releases, the proposed external uploads folder if present, Hostinger file backups, Git-tracked public images and the existing Cloudinary account. Restore backup files into a separate recovery workspace only; never restore the website or database over production. Local Git has 104 tracked upload paths, not a complete production inventory.
3. Produce a reviewable manifest per historical URL: source and source type, source size, SHA-256, actual MIME/image decode result, target reference if already known, current HTTP status, recovery state (`available`, `already healthy`, `conflict`, `missing source`) and proposed action. Reject traversal, symlinks outside approved sources and executable/unsupported content. Never infer a Cloudinary URL from a missing filename.
4. If two sources disagree for the same URL, compare against dates/checksums and backups; do not overwrite a newer upload. Keep all sources and mark the conflict for review. A missing original remains explicitly unrecoverable until a real source is provided or the owner reuploads it.
5. For available originals, propose a non-overwriting signed Cloudinary upload using the existing helper/account, with separate recovery public IDs. Deduplicate only after source checksums and reference counts are reviewed. Request approval for the exact batch of remote uploads before executing it; account quotas/costs apply. Do not delete sources or existing Cloudinary assets.
6. Record each actual successful upload's returned secure_url/public_id, source hash and downloaded target hash. Verify direct HTTP 200 and successful image decoding. Never mark a failed or unverified upload as recovered.
7. Preserve historical URLs until a separately approved mapping is active. Choices requiring an explicit decision are (a) a version-controlled, audited exact-path redirect map for verified public originals, or (b) narrow database URL updates restricted to reviewed rows and expected previous values. Neither is implemented or executed by this change. Do not create a generic Cloudinary redirect for every `/uploads/...` filename: that would fabricate missing assets and could expose private paths.
8. Before any approved database reference update, obtain a verified backup and test restore; use exact row IDs and optimistic old-value conditions, log counts, and retain the reverse mapping for rollback. No schema migration or full restore is needed. Never include Services migrations or modify orders/payments.
9. Verify original URL compatibility, new target HTTP 200, image checksums, actual pages and a controlled staging restart/redeployment. Retain original files and the audit manifest. Physical orphan deletion is out of scope and requires its own reference-aware review/approval.

Current recovery result: no live inventory or recovery performed because authenticated SSH is unavailable. Existing local images and database references were not deleted or rewritten. Exact missing production paths cannot be truthfully listed until the read-only reference/file inventory is available.
